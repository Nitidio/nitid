# Nitid Studio API contract (v1)

This directory is the **agreed interface** between the Studio frontend (`studio/`) and the local
FastAPI backend (`nitid/studio/`). It exists so both can be built in parallel and verified against the
same document. Decision record: [ADR-0005](../../docs/adr/0005-nitid-studio.md).

| File | What it is |
| ---- | ---------- |
| `openapi.json` | OpenAPI 3.1 description of `/api/v1`: endpoints, schemas, error envelope, embedded examples. |
| `onnx-meta.schema.json` | JSON Schema 2020-12 for the descriptor that travels with every ONNX export. |
| `fixtures/*.json` | Valid and invalid examples. The tests use them as a specification by example. |

## Status of `openapi.json`

This file is **hand-maintained for now**. The definitive document will be **generated by FastAPI**
from the backend once it exists. At that point:

1. The generated file replaces this one (same path).
2. The frontend generates its TypeScript types from it.
3. CI regenerates the document and **fails if it differs** from the committed copy, so the contract
   cannot drift silently from the implementation. [NV: the CI job is not written yet.]

Until then, the backend must conform to this file, not the other way round. A deliberate change to the
contract is a change to this file, to the fixtures and to the tests, in one commit.

## Validate

From the repository root, with the dev dependencies installed (`jsonschema`, `openapi-spec-validator`):

```bash
python -m pytest tests/unit/studio -q
```

The tests check that:

- `openapi.json` is valid OpenAPI 3.1 and every `$ref` resolves (no external references);
- `onnx-meta.schema.json` is a valid 2020-12 schema;
- every `example` embedded in the OpenAPI document validates against its own schema;
- each `fixtures/<kind>.*.valid.json` passes and each `*.invalid.*.json` fails for its kind;
- the `OnnxMeta` component inside `openapi.json` and the standalone schema accept and reject the same documents;
- the endpoint list, bearer security (with public `/health`), the shared error envelope, the upload
  limits and the ETag behaviour are all present.

## Fixture naming

`<kind>.<name>.valid.json` must validate. `<kind>.invalid.<rule>.json` must fail the schema, one file
per rule being protected (for the meta: dtype, range, colour order, resize mode, shape, outputs per
task, box format, mask stride, class names, `sha256` format, and so on).
`<kind>.invalid-semantic.<rule>.json` must **pass** the schema but fail the cross-field check in
`test_contract.py` (`meta_semantic_errors`): JSON Schema cannot say "`input.shape` equals
`[1, 3, imgsz, imgsz]`", so producers and consumers must check it in code.

Kinds: `meta`, `health`, `devices`, `models`, `job`, `run-params`, `run`, `error`.

## Conventions worth knowing

- **Auth**: `Authorization: Bearer <token>`; the token is generated at each launch. `/health` is the
  only unauthenticated endpoint. Host and Origin are validated too (403 `forbidden_origin`).
- **Errors**: always `{"error": {"code": "snake_case", "message": "..."}}`.
- **Models** are `(id, task)` pairs: `nitid1s` appears once for `detect` and once for `segment`.
  Downloads therefore take `?task=`.
- **Items**: `items[].id` is zero-based and equals the `{n}` in `/runs/{id}/items/{n}...`.
- **Box coordinates** in run results are pixels of the *original* image; boxes inside the ONNX output
  are pixels of the *model input* (`xyxy_input_px`) and must be rescaled by the consumer.
- **ONNX ETag** is the lowercase sha256 of the body, quoted (`"<hex64>"`). `sha256` in the meta
  returned by `/onnx/{model}/meta` is the same value; it is never embedded in the ONNX itself.
- **Limits**: 25 MB and 20 Mpx per image, rejected with 413 before decoding.
- Items marked `[NV]` in descriptions are not verified against an implementation yet.

## Changing the contract

Additive, backwards-compatible changes (a new optional field, a new endpoint) stay in `v1`. Anything
else (removing or renaming a field, tightening a type) needs `/api/v2` and a new ADR. For the meta,
bump `schema_version` and keep reading version 1.
