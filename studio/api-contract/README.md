# Nitid Studio API contract (v1)

This directory is the **agreed interface** between the Studio frontend (`studio/`) and the local
FastAPI backend (`nitid/studio/`). It exists so both can be built in parallel and verified against the
same document. Decision record: [ADR-0005](../../docs/adr/0005-nitid-studio.md).

| File | What it is |
| ---- | ---------- |
| `openapi.json` | OpenAPI 3.1 description of `/api/v1`: endpoints, schemas, error envelope, embedded examples. |
| `onnx-meta.schema.json` | JSON Schema 2020-12 for the descriptor that travels with every ONNX export. |
| `fixtures/*.json` | Valid and invalid examples. The tests use them as a specification by example. |

## Status of `openapi.json`

This file is **hand-maintained for now**. The definitive document will be **generated by FastAPI**
from the backend once it exists. At that point:

1. The generated file replaces this one (same path).
2. The frontend generates its TypeScript types from it.
3. CI regenerates the document and **fails if it differs** from the committed copy, so the contract
   cannot drift silently from the implementation. [NV: the CI job is not written yet.]

Until then, the backend must conform to this file, not the other way round. A deliberate change to the
contract is a change to this file, to the fixtures and to the tests, in one commit.

## Validate

From the repository root, with the dev dependencies installed (`jsonschema`, `openapi-spec-validator`):

```bash
python -m pytest tests/unit/studio -q
```

The tests check that:

- `openapi.json` is valid OpenAPI 3.1 and every `$ref` resolves (no external references);
- `onnx-meta.schema.json` is a valid 2020-12 schema;
- every `example` embedded in the OpenAPI document validates against its own schema;
- each `fixtures/<kind>.*.valid.json` passes and each `*.invalid.*.json` fails for its kind;
- the `OnnxMeta` component inside `openapi.json` and the standalone schema accept and reject the same documents;
- the endpoint list, bearer security (with public `/health`), the shared error envelope, the upload
  limits and the ETag behaviour are all present.

## Fixture naming

`<kind>.<name>.valid.json` must validate. `<kind>.invalid.<rule>.json` must fail the schema, one file
per rule being protected (for the meta: dtype, range, colour order, resize mode, shape, outputs per
task, box format, mask stride, class names, `sha256` format, and so on).
`<kind>.invalid-semantic.<rule>.json` must **pass** the schema but fail the cross-field check in
`test_contract.py` (`meta_semantic_errors`): JSON Schema cannot say "`input.shape` equals
`[1, 3, imgsz, imgsz]`", so producers and consumers must check it in code.

Kinds: `meta`, `health`, `devices`, `models`, `job`, `run-params`, `run`, `error`.

## Conventions worth knowing

- **Auth**: `Authorization: Bearer <token>`; the token is generated at each launch. `/health` is the
  only unauthenticated endpoint. Host and Origin are validated too (403 `forbidden_origin`).
- **Errors**: always `{"error": {"code": "snake_case", "message": "..."}}`.
- **Models** are `(id, task)` pairs: `nitid1s` appears once for `detect` and once for `segment`.
  Downloads therefore take `?task=`.
- **Items**: `items[].id` is zero-based and equals the `{n}` in `/runs/{id}/items/{n}...`.
- **Box coordinates** in run results are pixels of the *original* image; boxes inside the ONNX output
  are pixels of the *model input* (`xyxy_input_px`) and must be rescaled by the consumer.
- **ONNX ETag** is the lowercase sha256 of the body, quoted (`"<hex64>"`). `sha256` in the meta
  returned by `/onnx/{model}/meta` is the same value; it is never embedded in the ONNX itself.
- **Limits**: 25 MB and 20 Mpx per image, rejected with 413 before decoding. At most 50 files per run.
- Items marked `[NV]` in descriptions are not verified against an implementation yet.

## Changing the contract

Additive, backwards-compatible changes (a new optional field, a new endpoint) stay in `v1`. Anything
else (removing or renaming a field, tightening a type) needs `/api/v2` and a new ADR. For the meta,
bump `schema_version` and keep reading version 1.

## Raw (non-postprocessed) outputs

An ONNX exported with `postprocess=False` exposes the raw decoder outputs. Its embedded meta describes
them with the `raw_*` definitions: `pred_logits` (float32), `pred_boxes` (float32, normalised
`cxcywh`, format tag `cxcywh_norm`) and, for `segment`, `pred_masks` (float32, stride 4). The
postprocessed layout (`labels`, `boxes`, `scores`[, `masks`]) and the raw layout are the only two
accepted; mixing them is invalid. The API always serves postprocessed ONNX files; the raw layout is
described for completeness because the exporter embeds a meta in both cases.
Found while integrating the `studio/onnx-meta` branch (the exporter produced raw layouts the first
schema version rejected); see fixtures `meta.*-raw.valid.json` and `meta.invalid.raw-*.json`.

## Runs (implemented in `nitid/studio/runs.py`, `routes_runs.py`)

`POST /runs` takes `files` plus a JSON `params` part (`RunParams`) and answers `202 {"id"}`.
Behaviour the schema alone does not say:

- **Queue**: one inference at a time, in submission order; a queued run is `pending`.
- **`item_count`** is the number of uploaded files, `items` the results done so far.
- **Defaults** for omitted params: `conf` 0.25, `iou` 0.85, `imgsz` 640, `classes` null,
  `mask_threshold` 0.5, `device` null, `frame_step` 1. Unknown keys are `422`.
- **Files** are sniffed from their bytes: JPEG, PNG, WEBP, BMP. Anything else, video included,
  is `415`. (Video is not implemented yet.)
- **Status codes of `POST /runs`**: 202, 409 (official model not downloaded), 413, 415, 422.
  `409` was added to the original list; it is additive.
- **`Detection.segments`** (optional, only when `has_mask`): `{"x": [...], "y": [...]}` outline in
  original-image pixels. Additive to v1.
- `GET /runs/{id}/items/{n}.json`, `/items/{n}/image`, `/export.csv`, `/export.zip` and
  `DELETE /runs/{id}` follow the schema; an unknown run or item index is `404`.

## Error codes in use

`unauthorized` (401), `forbidden_host` / `forbidden_origin` (403), `not_found` (404),
`method_not_allowed` (405), `conflict` (409), `payload_too_large` (413),
`unsupported_media_type` (415), `invalid_params` (422), `internal_error` (500). Errors raised by
the framework under `/api/v1` (unknown path, wrong method, malformed multipart) use the same
envelope. `Health.api_version` is the **integer** `1`.

## Conformance tests

`tests/integration/studio/test_runs_api.py` drives the real app with tiny checkpoints built at
runtime and validates every response against the operation's schema in `openapi.json`
(including that the status code is documented). It also asserts that every `/api/v1` route the
app exposes exists in the contract.

## Implementation notes: ONNX endpoints

Implemented in `nitid/studio/routes_onnx.py` and `nitid/studio/onnx_service.py`; tested by
`tests/integration/studio/test_onnx_api.py` (responses validated against `openapi.json` and
`onnx-meta.schema.json`). Details and `curl` examples: [`docs/studio.md`](../../docs/studio.md).

- Paths are `GET /onnx/{model}` and `GET /onnx/{model}/meta` with `task` (required) and `imgsz`
  (optional) as query parameters, exactly as in `openapi.json`.
- `imgsz` default (marked `[NV]` in the contract) is now defined by the implementation: the
  checkpoint's own `eval_spatial_size` when it is a multiple of 32 in 32-4096, otherwise 640.
- The binary has a strong `ETag` (`"<sha256>"`) and honours `If-None-Match` (including `*` and
  `W/` forms). The meta response carries the same `ETag` header; its body is the embedded
  `nitid_meta` plus `sha256`, and nothing else (the schema forbids extra properties, so there is
  no `size` field; use the binary's `Content-Length`).
- Beyond what the contract lists: `422 invalid_params` (bad `task`/`imgsz`) and
  `500 internal_error` (failed export) can be returned by both operations, and `Cache-Control:
  private, no-cache` is sent. A request for a model that is not downloaded is a `404 not_found`
  whose message points to the download endpoint. Candidates for an additive contract update:
  declare the 422 and 500 responses on both operations.
- `Range` is not part of the contract. Byte-range requests happen to work (`206`) because the file
  is served with Starlette's `FileResponse`; clients must not depend on it.
- No endpoint to upload a user-provided ONNX is defined by the contract, so none exists.
